## Sign-up aur sign-in (TASKS T3.1 PR 2 + 3, ARCHITECTURE §7.1)

Owner ke faisle (2026-10-27): **sabhi 11 apps email + password se sign-in** karte hain, sign-in me email code nahi. Email code sirf sign-up (email pakka karne ke liye) aur password set/reset me. Ek account, ek password, sabhi apps me. Authenticator (TOTP) 7 internal apps me har sign-in pe zaroori (pehli baar wahin lagta hai), baaki me optional; ek baar laga to har app maangta hai. Routes (contracts, sab `public`, gateway ki `otp`/`auth` rate limits):

| Route                                    | Apps                      | Kaam                                                                                                                                                                                                                                                                                                              |
| ---------------------------------------- | ------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `POST /auth/sign-up/code`                | customer, seller, creator | Sign-up ka code. Har email ko code jaata hai (account pehle se ho to wo code ke baad hi pata chalta hai). Consent har baar (`consentProblems`): terms + privacy, customer me 18+ bhi.                                                                                                                             |
| `POST /auth/password/code`               | sab                       | Password set/reset ka code (pehla password: Google wala account, rider, staff; ya bhool gaya). Anjaan email pe kuch nahi jaata, jawab wahi aur utne hi samay me.                                                                                                                                                  |
| `POST /auth/otp/:challengeId/resend`     | sab                       | Naya code (purana band): max 3, ek minute ke gap se.                                                                                                                                                                                                                                                              |
| `POST /auth/otp/:challengeId/verify`     | sab                       | `{ code, password }`. 5 try; sahi code ek hi baar. Leaked password (HIBP) code khatam hone se pehle mana. `outcome`: `account-made` (naya account, signed in), `password-set` (password code, ya bina password wala account), `password-kept` (account me password pehle se: nahi badla, us app ka consent juda). |
| `POST /auth/login`                       | sab                       | `{ email, password }` → `next`: `signed-in`, `totp` (authenticator hai) ya `totp-enroll` (internal app, abhi nahi laga) + `loginId` (5 min; lagane ke liye 10).                                                                                                                                                   |
| `POST /auth/login/:loginId/totp`         | sab                       | Authenticator code; har code ek baar (pichhla time step DB me).                                                                                                                                                                                                                                                   |
| `POST /auth/login/:loginId/recovery`     | sab                       | 10 recovery codes me se ek (`ABCDE-FGH23`), har code ek baar; bache hue ginti me.                                                                                                                                                                                                                                 |
| `POST /auth/login/:loginId/totp/enroll`  | sab                       | Naya secret + `otpauth://` link (QR browser me banta hai). Dobara maangne pe naya secret.                                                                                                                                                                                                                         |
| `POST /auth/login/:loginId/totp/confirm` | sab                       | Pehla sahi code authenticator save karta hai: 10 recovery codes (sirf ek baar dikhte hain), signed in.                                                                                                                                                                                                            |

- **Collections:** `identity_users` (account, har role ka ek hi), `identity_credentials` (`_id` = userId: password ka argon2id hash, TOTP secret `IDENTITY__FIELD_KEYS` se sealed + `lastStep`, recovery codes ke HMAC), `identity_auth_providers` (login ke tareeke: `password`, `google`, `linkedin`, `github`; `subject` = provider ka user id; unique `(userId, provider)` aur `(provider, subject)`), `identity_legal_acceptances` (consent: naya account, us app me pehli baar, naya legal version, pehli 18+ declaration).
- **Password** ([src/password.ts](src/password.ts)): `passwordZod` (trim, 12–128). argon2id Node ke `crypto.argon2` se, OWASP minimum (19 MiB, t=2, p=1), **ek waqt me ek hash** (32 se zyada intezaar = 503); purani settings wala hash agle sahi sign-in pe naya. HIBP range API (sirf SHA-1 ke pehle 5 hex bahar, padding ke saath), 2 s timeout, na mile to password chalta hai + warning log (fail-open). `IDENTITY__HIBP_URL` optional (tests nakli server pe).
- **Ek jaisa jawab:** galat email, galat password, bina password ka account (sirf Google) aur locked account: sab `INVALID_CREDENTIALS` 401, aur password hamesha check hota hai (anjaan email pe ek nakli hash se), isliye samay bhi ek jaisa. Code maangna/resend min 400 ms (`OTP_MIN_ANSWER_MS`).
- **Rok** ([src/lockout.ts](src/lockout.ts)): 15 min me 10 galat (password, authenticator, recovery code sab gine jaate hain) → us account pe 1 ghanta rok, jawab wahi. Ginti sirf poore sign-in ke baad reset (sirf sahi password se nahi, warna authenticator ko naye try milte). Email code se naya password rok hatata hai. Keys me email nahi, uska HMAC.
- **Session:** har sign-in ka aakhri step `SessionPort.issue` ([src/sessions.ts](src/sessions.ts)). Abhi sirf naam lautata hai, koi cookie nahi; asli session T3.2 me, "us app ka grant hai?" check T3.3 me.
- Code Redis me sirf hash (`bq:id:otp:<challengeId>`, 10 min TTL); notify tak event `identity.otp.requested` me **sealed** (`IDENTITY__OTP_EVENT_KEYS`), purpose `sign-up` ya `password`. Ek email ke ek ghante me max `IDENTITY__OTP_EMAIL_LIMIT_PER_HOUR` (5) codes. Redis band = 503.
- Errors (`IDENTITY_ERROR_CODES`): `OTP_*`, `INVALID_CREDENTIALS`, `PASSWORD_BREACHED`, `LOGIN_EXPIRED`, `TOTP_INVALID`, `RECOVERY_CODE_INVALID`; text ek jagah [src/errors.ts](src/errors.ts).
- Mutations (RULES §6, login): `npm run mutate -- --package identity` ([test/mutations.ts](test/mutations.ts)). Tests asli Mongo + Valkey pe, HIBP ka nakli server ([test/helpers.ts](test/helpers.ts)); internet kabhi nahi.

## Sessions (TASKS T3.2, ARCHITECTURE §7.2)

- Har sign-in (password, authenticator, recovery code, authenticator lagana, naya account) ke aakhir me `identity_sessions` me ek session aur app ki do cookies: `__Host-bq_<app>_at` (ES256 access token, 10 min, Path /, Lax) aur `__Secure-bq_<app>_rt` (refresh, Path `/api/v1/auth`, Strict). Dono HttpOnly + Secure, Domain nahi. Jawab ke body me koi token nahi.
- Session ki lambai `SESSION_POLICIES` (contracts): customer/creator 30 din, har refresh pe aage, max 90; seller 7; delivery 14; internal 12 ghante aur 30 min idle.
- `POST /auth/refresh`: naya token pair, purana band. Purana token 10 s ke andar = parallel tab (409 `REFRESH_IN_PROGRESS`); baad me = chori: session band, Redis `bq:id:session-revoked:<sid>`, event `identity.session.reuseDetected` → notify ka "We signed you out" email. Session khatam (idle/expire) ho chuka ho to chupchaap `SESSION_EXPIRED`, alarm nahi.
- `POST /auth/logout`: session band + Redis key + cookies saaf. Email code se naya password = account ke **saare** sessions band + `bq:id:user-revoked:<userId>`.
- Token keys: `identity_signing_keys`, private key `IDENTITY__FIELD_KEYS` se sealed, har 30 din nayi; `GET /.well-known/jwks.json` (sirf gateway ke liye, `/api` route nahi).
- Signed-in routes gateway ke passport se (`X-BQ-Passport`, server-kit `passportVerifier`; bundle gateway ki public key memory me deta hai, split mode me `IDENTITY__PASSPORT_JWKS_URL`): `GET /iam/me` (account, login ke tareeke, authenticator, ye session), My Devices `GET /auth/sessions` (account ke saare apps ke sessions, current ka nishaan), `DELETE /auth/sessions/:id` (ek device; apna ho to cookies bhi), `POST /auth/sessions/end-others`.

## Roles aur grants (TASKS T3.3, ARCHITECTURE §7.3)

- **Data, code se:** har start ka release step `rbac-sync` 11 apps (`identity_apps`), permission catalogue (`identity_permissions`, contracts ka `permissions`) aur `src/rbac/roles.ts` ke roles (`identity_roles`, `system: true`) DB me likhta hai. PRD §3.2 ke 79 roles + 2 sign-up roles (`seller.applicant`, `creator.applicant`). Code se hata role/key `retired` banta hai, mitta nahi. Master ke banaye sub-roles (`system: false`) ko sync nahi chhoota.
- **Har role me:** app, main ya sub, scope types, permission keys (hamesha `iam.app.sign_in`), kaun de sakta hai (`appointedBy`; ARCHITECTURE §7.3, baaki sub-roles Master), `mfaRequired` (Seller Account Owner, Seller Finance, Master), seats (Master 2). Naya module apni keys yahin roles me jodta hai; `roleSeedProblems()` (test bhi) anjaan key, scope ke bahar ki key ya aisa appointer jo role nahi de sakta, pakadta hai.
- **Grants** (`identity_grants`): `{userId, role, app, scope {type, ids}, validFrom, validTo, grantedBy, approvedBy, via, active}`; ek account, role aur scope id pe ek hi active. Har badlav `identity_grant_log` me aur account ka `authzVersion` badhata hai, jo access token ka `av` hai.
- **Sign-up pe:** customer app me 18+ ke baad Customer, seller/creator me applicant (scope self), pehle se bane account ko bhi. Purane accounts ko migration `20261029-001-sign-up-grants` ne yahi diya.
- **Sign-in sirf us app me jahan grant ho:** password sahi ho par us app me active grant na ho to wahi jawab jo galat password pe (`INVALID_CREDENTIALS`), aur ye galat koshish nahi ginta. `SessionPort.issue` bhi yahi check karta hai (koi raasta bina grant ke session nahi bana sakta). Refresh pe grants dobara: app me koi grant na bache to session band (`access-ended`) aur `SESSION_EXPIRED`. Kisi grant ka role `mfaRequired` ho to authenticator lagana zaroori, internal apps ki tarah.
- **Pehla Master:** `npm run db:grant-master -- --email <email>` ([backend/bundle/README.md](../bundle/README.md)); account pehle se ho, max 2.
- **States:** `state` scope ke ids contracts ke `INDIAN_STATES` (28 states + 8 UTs, 2-letter id, GST code). District, city, hub aur warehouse ke ids location master ke saath.

### Roles dena aur hatana (T3.3 PR B, `src/rbac/manage.ts`, `authority.ts`)

Routes (contracts `catalogue/iam.ts`), sab gateway ke passport se; identity khud apne grants se jaanchta hai ki caller kar sakta hai ya nahi (caller ke grants usi app ke gine jaate hain jahan se wo aaya, passport ka `app`). Gateway pehle mota check karta hai (neeche "Gateway ka check aur step-up"), phir identity apna poora check.

| Route                                                      | Kaun                                                                                                                                                                        |
| ---------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET /iam/roles`                                           | `iam.grant.read` wala                                                                                                                                                       |
| `POST /iam/roles`, `PATCH /iam/roles/:roleKey`             | `iam.role.manage` (Master). Key `<app>.c_<slug>`; shipped role sirf code se badalta hai                                                                                     |
| `GET /iam/grants`                                          | `iam.grant.read`: appointer ko wahi roles jo wo deta hai, apne scope me; reviewer (Security Officer, Internal Auditor: padhte hain, dete nahi) ko saare roles apne scope me |
| `POST /iam/grants`, `POST /iam/grants/:grantId/end`        | `iam.grant.manage` + caller ka role us role ke `appointedBy` me + naya scope caller ke scope ke andar (`scopeWithin`)                                                       |
| `POST /iam/invitations`, `GET`, `.../:invitationId/revoke` | grant jaisa hi                                                                                                                                                              |
| `POST /auth/invitations/code`                              | public: invite accept karne ka email code                                                                                                                                   |

- **Niyam (separation of duties):** koi khud ko role nahi deta, apna role khud khatam nahi karta, khud ko invite nahi karta. Retired role diya nahi jaata. `self` scope sirf usi account ka. State ka id `INDIAN_STATES` me ho; district/city/hub/warehouse abhi nahi (location master). Khatam grant record me rehta hai (`active: false`, `identity_grant_log`).
- **Turant asar:** har grant badlav pe account ka `authzVersion` +1, aur commit ke baad Redis `bq:id:authz-version:<userId>` (contracts `authzVersionKey`, ~11 min). Gateway purane `av` wala token 401 karta hai; app refresh karti hai aur naya token naye grants ke saath aata hai (app me koi grant na bacha to session band). Custom role ke permissions/scope/authenticator/retired badalne pe uske saare holders ka version badhta hai.
- **Custom role:** `roleProblems` (shipped jaisa hi check) + `iam.role.manage` nahi; jis role ko doosre roles apna appointer maante hain, us se `iam.grant.manage` hatana ya use retire karna 409; jo scope type kisi active grant me hai, use hatana 409.
- **Invitations** (`identity_invitations`, `src/rbac/invitations.ts`): email pe, 7 din. Banne pe outbox event `identity.invitation.created` → notify ka "You are invited" email (koi secret nahi). Accept: role ke app me `POST /auth/invitations/code` (sirf us email pe jiske liye is app me invitation ho; sign-up apps me unki consent) → `POST /auth/otp/:challengeId/verify` (code + password) → `invite-accepted`: naya account password ke saath, pehle se password wala account apna password rakhta hai; grant `via: 'invitation'`, `grantedBy` = inviter. Sign in nahi hota: app ka login (authenticator ke saath) agla. Accept ke waqt inviter ka haq dobara dekha jaata hai: haq gaya to invitation `revoked`. `self` scope invitation me ids khaali, account ka id accept pe.
- **Abhi ki seema:** alag type ka scope (State Admin, scope `state`, se Seller Account Owner, scope `sellerOrg`, ya Pro Buyer, scope `self`) tab tak koi nahi de sakta jab tak seller/pro module nahi batata ki wo org/buyer kis state me hai (unke approval flow ke saath, T4). Master inka appointer nahi (PRD §3.6: seller approval me Master ka bypass nahi).

### Gateway ka check aur step-up (T3.3 PR C)

- **Permission list:** har sign-in, refresh aur step-up pe identity Redis me `bq:id:perms:<userId>:<app>` (contracts `appPermissionsKey`) likhta hai: `{ v: authzVersion, keys }` (us app ke active grants ke non-retired roles ki keys), ~11 min. Gateway permission route pe: key ho to aage, na ho to 403; list na ho ya doosre `av` ki ho to 401 (app refresh karti hai, identity list dobara likhta hai). Scope ka check service ka (T4.1).
- **Step-up:** session ka `stepUpAt` (authenticator ya recovery code se sign-in, ya `POST /auth/step-up`), access token me `su`; refresh use rakhta hai. Route ka `stepUp` ho to gateway 5 min (`STEP_UP_SECONDS`) ke andar ka step-up maangta hai, warna 401 `STEP_UP_REQUIRED`. `POST /auth/step-up`: `{ code }` (authenticator) ya `{ recoveryCode }` (phone kho gaya; code khatam, jawab me `recoveryCodesLeft`). Galat wala account ke lock me gina jaata hai; locked account nahi; purana ya wahi code dobara nahi; authenticator na ho to `AUTHENTICATOR_REQUIRED`. Sirf naya access cookie. `stepUp` ab `signed-in` routes pe bhi (apne account ke kaam, neeche).
- **Security Officer** (`src/rbac/security.ts`): `POST /iam/users/:userId/authenticator/reset` (authenticator + recovery codes hat'te hain, saare sessions band, event `identity.authenticator.reset` → notify ka email), `POST /iam/users/:userId/sessions/end`. Apne account pe nahi. Person ko email se: `GET /iam/grants?email=`.

### Apna authenticator, signed in (ARCHITECTURE §9.2, `src/authenticator.ts`)

| Route                                     | Step-up | Kaam                                                                                                                                                                                                                                 |
| ----------------------------------------- | ------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `POST /auth/authenticator/enroll`         | nahi\*  | Naya secret + otpauth link; Redis me sealed `bq:id:totp-setup:<sessionId>`, 10 min, 5 try. Password ke bina account: `PASSWORD_REQUIRED`. \*Authenticator pehle se ho to **badalna**: identity session ka taaza step-up maangta hai. |
| `POST /auth/authenticator/confirm`        | nahi    | `{ code, password }`: 10 naye recovery codes (ek baar dikhte), purane band. Galat password/code lock me gina jaata hai; 5 galat pe set-up khatam. Beech me doosre tab ne lagaya to `AUTHENTICATOR_EXISTS`.                           |
| `POST /auth/authenticator/recovery-codes` | haan    | 10 naye codes, purane band.                                                                                                                                                                                                          |
| `DELETE /auth/authenticator`              | haan    | Authenticator + codes hat'te hain. Koi active grant zaroori maange (TOTP_REQUIRED_APPS ke roles, ya `mfaRequired` role jaise Seller Finance; retired role nahi) to 409 `AUTHENTICATOR_REQUIRED_BY_ROLE`, roles ke naam ke saath.     |

- Har badlav pe event `identity.authenticator.changed` (`enabled`, `replaced`, `recovery-codes`, `disabled`; app + device) usi transaction me → notify ka security email. Sessions chalte rehte hain. Gateway step-up route pe token ka `su` dekhta hai; identity bhi session ka `stepUpAt` dobara jaanchta hai.
- `GET /iam/me` me `recoveryCodesLeft` (authenticator na ho to `null`).

## Settings

`.env.example` ka LOCAL hissa `.env` me copy karo (commit kabhi nahi); OPTIONAL me defaults, PRODUCTION me live ki keys dummy values ke saath. Har key `IDENTITY__` se shuru hoti hai, taaki bundle mode me ek process me sab deployables ki keys alag rahein. Settings sirf [src/config.ts](src/config.ts) padhta hai (zod se check; ESLint baaki jagah `process.env` rokta hai). Nayi setting = `configZod` me key + `.env.example` me line.

## Code kahan hai

- `src/service.ts`: `readConfig` + `start` (split mode me `src/server.ts`, bundle mode me `backend/bundle` isse chalata hai).
- `src/release.ts` + `src/runtime.ts`: start pe Mongo se judte hi release steps (migrations, indexes; `@beautinique/backend-server-release`, ARCHITECTURE §11.1), phir Redis. Nayi migration list ke aakhir me, naye collection ke indexes `indexes` me; step `rbac-sync` (T3.3).

- `src/routes/index.ts`: identity ke routes (app `X-BQ-App` se, IP `X-BQ-Client-Ip` se, dono gateway ke). Har route contracts me declare hota hai (owner `identity`), yahan sirf handler.
- `src/otp.ts`: email code maangna, naya code, check + password (Redis + outbox). `src/login.ts`: password sign-in, authenticator, recovery codes, step-up. `src/authenticator.ts`: apna authenticator (lagana, badalna, naye codes, band). `src/password.ts`: argon2id + HIBP. `src/lockout.ts`: galat koshishein aur rok. `src/credentials.ts`: secrets aur login ke tareeke. `src/users.ts`: accounts aur consent. `src/sessions.ts`: sessions, refresh rotation, logout. `src/signing-keys.ts`: token keys + JWKS. `src/cookies.ts`: cookies. `src/errors.ts`: error text. `src/rbac/`: roles (`roles.ts`), apps/permissions/roles ka sync (`sync.ts`), grants aur sign-in ka check (`grants.ts`), migration, pehla Master (`bootstrap.ts`).

Node 24 TypeScript seedha chalata hai: imports me `.ts` likho, enum ya parameter properties nahi.
