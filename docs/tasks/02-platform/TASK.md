### 3.8 `backend-mongo`

1. Client aur transaction helper: snapshot read, majority write, transient error pe poora kaam dobara, commit anjaana ho to sirf commit dobara, kul misaal 10 second phir 503 ([ARCHITECTURE.md](../../ARCHITECTURE.md) §10.2 niyam 1 se 3).
2. Repository ka aadhar: `version` ke saath update aur 409, halat ki shart wale update, cursor pagination, `maxTimeMS` (§10.2 niyam 5 aur 6, §10.4 niyam 8).
3. Money codec (BSON `long`).
4. Release step: collections, validators, indexes aur fingerprint, lease ke peeche; schema wala hissa listen se pehle, lambi data migration baad me (§10.4 niyam 1 se 5).
5. Har collection ki retention class ki registry; bina class ya bina delete handler ke collection pe CI fail (§10.3 niyam 1).
6. Har repository query ke `explain` aur collection scan ke pehre ka helper ([OPERATIONS.md](../../OPERATIONS.md) §2 niyam 6).

Code ka roop (ST-6): `createMongoClient({ uri, appName, maxPoolSize })`: majority write aur read, retryable writes aur reads, server dhoondhne ke 5 second, `undefined` field chhoda jaata hai; `maxPoolSize` har service khud deti hai. `withTransaction(client, work, { clock, deadlineMs? })`: snapshot read aur majority write, primary se; transient error (write conflict, naya primary) pe poora kaam ek chhote random intezaar ke baad dobara; commit ka nateeja anjaana ho to sirf commit dobara; 10 second (`TRANSACTION_DEADLINE_MS`, injected ghadi se) ke baad 503 (`SERVICE_UNAVAILABLE`, `Retry-After` 5); commit apne 2 second (`COMMIT_MAX_TIME_MS`) me na ho to turant 503, kyunki commit hua ya nahi ye pata nahi (dobara aayi request ko idempotency sambhalti hai); query ka `maxTimeMS` khatam ya database na mile to bhi 503; baaki error waise hi. `mongoCall(run, session?)`: database na mile to 503, par transaction ke andar error waisa hi, taaki dobara koshish ho. Repository: `updateVersioned(collection, { id, version, where? }, update)` (filter me id, version aur purani halat; version khud ek badhta hai, update me `version` mana; mel na ho to 409 `CONFLICT`, server-kit ka naya `conflict()`), `updateIf` (shart wala badlav, jaise counter pe conditional `$inc`; mel na ho to `null`), `findPage` (cursor se, `skip` nahi; `limit` 1 se 100; `by` aur phir `_id` ke kram me; cursor `[by, value, _id]` canonical Extended JSON me, base64url, to date date hi rehti hai; doosri list ka ya bigda cursor 400 `query.after`); har query pe `maxTimeMS` 2 second (`QUERY_MAX_TIME_MS`), transaction ke andar nahi (uski apni deadline). Money codec: `moneyToBson` (BSON `long`), `moneyFromBson(value, field)` (driver ke teeno roop: number, `Long` aur `bigint`; safe range me poore paise, galti me field ka naam aur value kabhi nahi), `MONEY_BSON_SCHEMA` (`long`, 0 ya zyada). Retention registry: `defineCollection({ name, retention, schema?, indexes, expiry, accountDelete })`: class saat me se ek (`RETENTION_CLASSES`), `expiry` (`ttlIndex`, `job`, ya `never` aur wajah; R-040 ka TTL wala hissa), `accountDelete` (`run` delete ke transaction me, ya `none` aur wajah); kuch kam ya galat ho to turant `RangeError`. `defineCollections(service, specs)`: ek naam do baar refuse, aur plan ka `fingerprint` (naam, schema aur indexes ka SHA-256; kram se nahi badalta). `retentionProblems(collections, names)`: CI ka pehra, database ki har collection jo registry me nahi (`system.*` chhod ke). Release step: `releaseSchema(db, collections, { clock, owner })` listen se pehle, `release` lease ke peeche: har collection apne validator (`strict`, `error`) aur indexes ke saath; wahi fingerprint to kuch nahi; doosra instance chala raha ho to intezaar, aur `RELEASE_WAIT_MS` (60 second) ke baad boot ruke; collection kabhi drop nahi; jo index plan me nahi wo drop (purana roop, naye naam ke agle release me, §10.4 niyam 2); naam wahi aur roop alag ho to release ruke. `runDataMigrations(db, migrations, { clock, owner, signal? })` listen ke baad: har `DataMigration` (`id`, `batch`) kram se, 50 ka batch (`MIGRATION_BATCH_SIZE`), 100 ops/second (`MIGRATION_OPS_PER_SECOND`), kahan tak hua `migrations` me, SIGTERM pe ruk ke agli baar wahin se; sirf ek instance (`release-data` lease), baaki ko `elsewhere`. Lease: `acquireLease` aur `releaseLease` (`leases` collection, unique `_id` pe ek atomic kadam; ST-7 ka dispatcher aur ticker bhi yahi lenge). Query plan ka pehra: `queryPlanProblems(collection, { name, filter, sort?, projection?, limit? })` asli database pe `explain` se `COLLSCAN`, memory me `SORT`, ya collection hi nahi pakadta; `planProblems` kisi bhi gehrai ka plan ek pass me (CR-40). ### 3.9 `backend-events`

1. Outbox usi transaction me; dispatcher nudge aur misaal 5 second ke poll se; bundle mode me handler call, split mode me signed HTTP ([ARCHITECTURE.md](../../ARCHITECTURE.md) §3 niyam 1 se 3).
2. Inbox: `processed_events` usi transaction me, asar theek ek baar (§3 niyam 4).
3. Ek aggregate ke events kram se; ek fail ho to sirf usi aggregate ke agle events rukein (§3 niyam 5, §10.2 niyam 10).
4. Retry backoff ke saath, misaal 8 koshish; phir dead letter aur ops alert; subscriber ka database band ho to ginti nahi badhti (§3 niyam 6, §10.2 niyam 11).
5. Timers, ticker aur leases: har due timer ek hi baar, boot pe sweep, chhoote din kram se (§4 niyam 1, 4 aur 6).
6. BullMQ ki queues: har service ki halki queue aur ek `heavy` queue; job id = record id; Valkey khaali ho to pending kaam dobara queue me (§4 niyam 2 aur 3).
7. Platform collections (`outbox`, `processed_events`, `dead_letters`, `timers`, `leases`) aur unke TTL (§10.2 ki table).

Code ka roop (ST-7): **Outbox:** `createOutbox({ service, subscriptions, clock })` ka `append(db, session, contract, event)` sirf transaction ke andar (bahar refuse, AC-PLATFORM-2); doosre producer ka event, contract se na milta (sandesh me field ka naam, value kabhi nahi) aur 16 KB se bada refuse. `eventId` ObjectId ke 24 hex, `occurredAt` injected ghadi se; envelope JSON text me rehta hai, har subscriber ko wahi bytes. Ek event ka ek document: har subscriber ki delivery (`status`, `attempts`, `nextAttemptAt`), `pendingCount`, sabse jaldi wala `nextAttemptAt` aur `doneAt` (sab delivered hone pe; TTL 7 din). Jis event ka koi subscriber nahi, wo turant done. Subscriber `<service>` ya `<service>.<naam>`; subscriptions boot pe jaanchi jaati hain. **Dispatcher:** `createDispatcher` `dispatcher` lease (30 second, lambe pass me naya; lease chhooti to pass rukta hai) ke peeche, ek pass me 100 tak due events, sabse jaldi wale pehle; ek aggregate ke events us subscriber ko kram se (aggregate ka version, phir likhne ka kram), aur pehla na gaya ho to agle rukte hain, baaki aggregates aur subscribers chalte rahte hain (AC-PLATFORM-4). Retry 1, 5, 15, 30, 60, 90 aur 150 minute ke baad (8 koshish, 5 ghante 51 minute); 8vi ke baad delivery `dead`. Subscriber band (uska database ya process) to 1 minute baad dobara, ginti nahi badhti (AC-PLATFORM-5). Dead delivery ke peeche ruke events har ghante dekhe jaate hain; `retryDeadDelivery` (Master app ka raasta, permission ke saath) use ginti 0 se dobara chalata hai aur uske peeche ruke events bhi turant. Har likhna usi halat pe jo padhi thi, to lease badalte waqt do instance ek doosre ka likha nahi mitaate. `nudge()` commit ke baad turant pass, warna 5 second ka poll. **Delivery:** `inProcessDelivery` (bundle) aur `signedHttpDelivery` (split: server-kit ke facade jaisa signed call `events.<subscriber>`, `POST /internal/events/<subscriber>`, 15 second; jawab nahi ya 5xx to `unavailable`, 4xx to `failed`); subscriber ki taraf `createInboxEndpoint` (pehle signature, phir body). **Inbox:** `createInbox` aur `onEvent(contract, handle)`, har event aur version ka ek handler (§3 niyam 9); handler ka asar aur `processed_events` (`<eventId>:<subscriber>`) ek transaction me, to wahi event 3 baar (ek saath bhi) aaye to asar ek (AC-PLATFORM-3). Jawab `delivered`, `failed` (handler ki apni galti, ya jo event koi handler nahi leta), `unavailable` (apna database band; ginti nahi) aur aakhri koshish pe `dead`: apne database me dead letter aur ops alert (`Alert` port, gambhirta 2); baad me le liya jaaye to usi transaction me dead letter `resolvedAt` (TTL 90 din). **Timers aur ticker:** `scheduleTimer` aur `cancelTimer` (change ke transaction me; ek kind aur ref ka ek pending timer, dobara set karne pe khisakta hai); `onTimer` ka kaam aur timer ka done ek transaction me, to do instance tick karein tab bhi har timer ek baar (AC-PLATFORM-6). `dailyJob({ kind, at, run })` har IST din ka ek timer ki chain: din D ka kaam agle IST din ke `at` ke baad, aur done hote hi agle din ka timer; naya job aakhri poore din se shuru, lambi neend ke baad har chhoota din kram se; bada kaam transaction ke bahar, 10 minute ke claim ke saath. `createTicker` `ticker` lease (2 minute) ke peeche har due timer ek baar, sabse jaldi pehle, jab tak koi due na bache (50 ke batch, ek tick 50 second tak); fail timer events jaisa retry, 8 ke baad `failed` aur alert; database band ho to ginti nahi. Pehla tick boot ke 30 second baad (sweep), phir har 60 second; tick ke ant me queues ka requeue. **Queues:** `createJobQueues({ connection, prefix, logger, alert })`, `service(service, { db, kinds })` aur `defineJob({ name, queue, pending, run })`: har service ki halki queue (concurrency 2) aur process ki ek `heavy` (concurrency 1). Job me sirf record ka id; job id `<kind>.<recordId>` (`jobIdOf`; sirf record id nahi, taaki ek queue me do kaam ka ek record id na takraaye); 5 koshish, 30 second se dugna intezaar, phir alert. `requeuePending()` (ticker se) DB me pending par queue me na hone wale records dobara daalta hai, aur jo job pehle se hai wo dobara nahi judta (AC-PLATFORM-7); `run` record ki halat pehle dekhta hai. Ek saajha Valkey connection (`createQueueConnection`, `maxRetriesPerRequest: null`) aur har worker ka ek: saare 12 services aur `heavy` ke saath 14 connections (jaancha), 20 ki seema ke andar; rate limit counter ka connection alag, jo Valkey band hone pe turant fail ho. **Collections:** `eventsCollections` (`outbox`, `processed_events` 14 din, `dead_letters`, `timers` done ke 7 din baad), `leasesCollection` (`backend-mongo`) ke saath; TTL ka kram (§10.2 niyam 12: `processed_events` outbox ke purge aur sabse lambe retry se lamba) test me. Logs aur alerts ke ports (`EventsLogger`, `Alert`): asli alerts operations ke module ke saath. Naye dependencies (OPERATIONS §11 niyam 2 ka review, 2026-11-27; D-001 ka stack, Node me Redis ka koi client nahi): `bullmq` 6.7.8 (peer aur dev; MIT, 1 maintainer (`manast`, BullMQ ka banane wala), 3.5 MB, 5 seedhe dependencies (`msgpackr`, `cron-parser` (jiska `luxon` 4.5 MB), `semver`, `tslib`, `node-abort-controller`), 2026-11-19 ka) aur `ioredis` 6.0.0 (peer aur dev; MIT, Redis ki team (4 maintainers), 1.3 MB, 6 seedhe dependencies, 2026-07-31 ka); naye wale (`bullmq` 6.7.10 aur `ioredis` 6.1.0) 7 din se kam purane the, to cooldown ke hisaab se ye. ### 3.10 `backend-crypto`

1. Field encryption AES-256-GCM, roop `v1.<keyId>.<iv>.<ciphertext>.<tag>`, associated data `<service>.<collection>.<field>:<recordId>`; key ke id ke saath, aur purane records ka re-encrypt (SR-063, [ARCHITECTURE.md](../../ARCHITECTURE.md) §10.3 niyam 5).
2. Blind index HMAC-SHA256, alag key se (§10.3 niyam 6).
3. Codes, recovery codes aur invite tokens ke hash (§10.3 niyam 7).
4. Rok ki copy ko public key se band karna; live server ke paas sirf public key (§10.3 niyam 4, SR-097).
5. Keys kabhi package me nahi; har service apne config namespace se deti hai.

Code ka roop (ST-8, D-469): naya dependency nahi, sab `node:crypto` se (Node 24.22.3, OpenSSL 3.5.9); teen entries: main (har service), `./mongo` (`sealed_records`) aur `./break-glass` (sirf owner ka laptop). **Keyring:** ek env key me `k2:<32 byte>,k1:<32 byte>` (base64url, sakht: padding ya badla akshar refuse), pehla current; 16 keys tak, id chhote akshar aur ank; ek hi key do baar ya ek id do baar refuse. `keyringSchema('<KEY>')` config ka zod schema (message me key ka naam, value kabhi nahi); keys `KeyObject` me, keyring log ya JSON me sirf naam aur ids dikhata hai. `newKeyText(id)` nayi key. **Field encryption:** `createFieldCipher({ service, keys })` ka `encrypt`, `decrypt`, `isCurrent`, `rotate`, `stalePrefixes`; AES-256-GCM, har baar nayi 12 byte IV, roop `v1.<keyId>.<iv>.<ciphertext>.<tag>`, associated data `<service>.<collection>.<field>:<recordId>` (service aur collection me `.` nahi, field me `.` par `:` nahi, record id me dono nahi: do jagah ka associated data kabhi ek nahi, property test); sirf poori string (toota surrogate refuse), 64 KB tak. Doosre record, field, collection, service ya keyring me, ya ek bhi akshar badla, to `CryptoError` (jagah aur key ka id, value kabhi nahi). Purani key ka value khulta hai, `rotate` use current key pe le jaata hai; roz ka batch (`_id` ke kram se, sirf jab purani key ho) service ke `dailyJob` me, README me tareeka. **Blind index:** `createBlindIndex` ka `indexOf` (`b1.<keyId>.<mac>`, HMAC-SHA256 `blind` key se, field ke context ke saath), `lookupValues` (har key ka index, `$in` ke liye), `isCurrent`, `stalePrefixes`. **Codes:** `createCodeHasher` (`blind` keyring, alag domain `code`) ka `hash` (`c1.<keyId>.<mac>`, context `<service>.<purpose>:<ref>`) aur `verify` (constant time; galat typed code ya anjaani key `false`, kabhi error nahi); purani key ka hash key ke rehte chalta hai. `hashToken` (22 se 1024 akshar ka random token, SHA-256), `randomToken` (16 se 1024 byte) aur `randomDigits` (4 se 12 ank, aage ke zero ke saath). **Band copy:** `createSealer({ service, key })` ka `seal(fields, { collection, recordId })`: har copy ki nayi X25519 key, HKDF-SHA256, AES-256-GCM, record associated data; roop `s1.<keyId>.<ephemeral key>.<iv>.<ciphertext>.<tag>`, 1 MB JSON tak. Public key config me `h1:<SPKI DER base64url>` (`sealingKeySchema`); usme private key (PKCS#8, PKCS#1, SEC1 ya PEM) to boot fail, aur `noPrivateKeysRule()` config ki kisi bhi text key me private key pakadta hai (SR-097). Sealer sirf band karta hai; main entry me kholne ka koi function nahi (test). `./break-glass`: `generateSealingKeyPair`, `parseOpeningKey`, `openSealed`. **`sealed_records` (`./mongo`):** `sealedRecordsCollection` (class `case`, `eraseAt_ttl`, `collection_recordId`, `accountId`; validator `sealed` sirf `s1.` roop me; account delete pe bhi rehta hai) aur `createHold({ sealer, collections, clock })` ka `hold(db, session, { collection, recordId, accountId?, fields, eraseAt })`: sirf transaction ke andar, registry me na ho ya `tech` class (D-321) ho to refuse, `eraseAt` abhi ke baad. Abhi nahi: roz ka re-encrypt ka asli job aur `/break-glass` ke import pe lint (pehli service ke saath), break-glass ka laptop command aur facade (operations aur pehli service ke saath), rok wali photos aur video ki streaming sealing (`06-media`), FY export ki sealing (finance, D-309), aur mutation ka run (ST-10).
