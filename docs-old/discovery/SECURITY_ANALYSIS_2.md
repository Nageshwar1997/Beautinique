## 2. Saupe gaye 7 items

### 2.1 `/wake` ka CSP apvaad (SR-005 bamuqabla wake endpoint)

**Finding:**

- SR-005 ka CSP `default-src 'self'` hai, to `connect-src` bhi sirf apna host. App `*.vercel.app` pe hai aur `/wake` seedha Render ke host pe jaata hai (ARCHITECTURE §5 niyam 14, D-349), to bina apvaad ke browser call rok dega.
- Sabse aasaan apvaad (poora Render host `connect-src` me) zaroorat se bada hai: XSS wali script Render ke har path tak pahunch sakti hai. `/api` waha SR-002 ke secret ke bina 403 deta hai, isliye bada nuksaan nahi, par zaroorat sirf ek path ki hai.
- CSP ke source me path diya ja sakta hai (bina aakhri `/` ke exact path). Par redirect ke baad path ka milaan nahi hota, isliye `/wake` kabhi redirect na kare (browsers ka vyavhaar F2-1 me jaanchna).
- CORS: cross-origin `fetch` ka jawab padhne ke liye server ko `Access-Control-Allow-Origin` dena padega. `*` aur credentials ka mel, ya har origin ko wapas bolna, galat hoga.
- Background ping (D-349 niyam 3) har khule tab se 10 minute me ek. Agar ping cookies le jaaye ya session ka "aakhri kaam" badhaye, to staff ka 30 minute idle (D-181) kabhi nahi lagega. `/wake` doosre host pe hai to app ki cookies waise bhi nahi jaati, par polling (ARCHITECTURE §5 niyam 7) signed-in routes pe hai (T2-08).
- `/wake` Redis ya database pe tika ho to jaagte waqt khud ruk jaayega; SR-007 pehle se kehta hai "na version, na database".

**Prastaav:** naya **SR-089** (§5.1): CSP ke `connect-src` me sirf `https://<gateway-host>/wake` (exact URL, wildcard nahi), sirf `GET`, `204` bina body, cookie aur version ke, koi DB ya Redis nahi, redirect kabhi nahi, CORS sirf apne apps ke exact origins bina credentials, IP pe process ke andar ki seema, service worker cache nahi kare. Saath me **SR-005 me badlav** (§5.2) aur **SR-094** (background requests idle nahi badhatin). ARCHITECTURE §5 niyam 14 ki line "`/wake` ke liye CSP ka apvaad Security Architect ke doosre run me" SR-089 ki link se badle (DC-17).

### 2.7 D-017 ka `+` alias (ek insaan, kai accounts)

**Kya pehle se sambhala hai:**

- D-203: alias wale accounts alag, par per-customer seemaon ke liye address, payment aur device ka jod; R1 me D-109 wala jod. D-255: device cookie sirf isi maqsad se.
- ARCHITECTURE §10.3 niyam 11: jod ka data sirf HMAC (`limits_link_keys`); account delete pe link keys delete.
- AC-COMMERCE-6 me alias wale accounts ek gine jaate hain; SR-046 D-204 ke zariye; SR-059 me D-203 (R2).
- D-203 bamuqabla SR-064 (UPI ID nahi rakhna): §10.3 niyam 11 ka HMAC isse sulajhata hai; Razorpay sthir pehchaan deta hai ya nahi, OPEN_QUESTIONS §2 me pehle se.

**Kya nahi sambhala:**

1. **Jod ka koi SR nahi:** device cookie ke flags (SR-027 sirf session ki cookies), address ka tay roop, aur "UPI ID kabhi nahi, sirf token ya fingerprint" SR me nahi. → **SR-093**.
2. **Email ka roop tay nahi:** ARCHITECTURE §10.7 niyam 1 `emailNorm` kehta hai par definition nahi (case, jagah, Unicode, domain). D-133 niyam 2 me "owner ke base emails aur unke `+` alias" ka milaan kaise hoga, aur testers ke alias chalenge ya nahi, likha nahi. Dhile milaan se `owner+x@gmail.com.evil.example` jaisa email allowlist me ghus sakta hai. → **SR-092**; testers ka sawal **S2-7**.
3. **Codes ki seemaon ka bypass:** D-187 ki seema "ek email ko ghante me 5" har alias pe alag lagti hai. Owner ke base email ke aliases allowlist me hain, to koi bhi `owner+1@...`, `owner+2@...` se sign-up ke codes bhej ke owner ka inbox bhar sakta hai aur sign-up ki din ki chhat (20) khatam kar sakta hai; testers ke sign-up us din ruk jaate hain. → SR-092 ki "mailbox key" seema aur SR-020 me badlav.
4. **Apne brand pe review (D-156, SR-059):** D-304 ke baad seller aur customer ke accounts alag hain, aur SR-059 sirf "wahi user ya wahi email" dekhta hai. Seller ka user `+` alias wale customer account se apne brand pe review likh sakta hai. → SR-059 me `emailNorm` aur mailbox key ka milaan (R1), aur D-203 ke ishare pe queue (R2).
5. **Referral (D-176, R2):** D-203 me pehle se gina hai; naya kaam nahi.

## 7. Proposed owner sawal

Sirf asli owner wale chunaav. S2-6 ka jawab S2-5 pe tika hai (group G2-A); baaki 8 kisi khule sawal pe tike nahi.

### S2-1. Kanooni rok aur band FY ki file ki chaabi kahan rahe?

- **Sawal:** kanooni rok me rakhe data (account delete ke baad ka, D-250), rok wali photos aur video (D-262) aur band FY ki export file (D-309) ko kholne wali chaabi live server ke paas ho, ya sirf laptop pe (offline)?
- **Kyun zaroori:** D-250 kehta hai ye data "sirf kanooni maang pe khule". Abhi ki design me chaabi live server ke env me hai, to server ki chaabiyon ka ek leak aur database ya media provider ki pahunch, dono milke sab khol dete hain. Delete hua personal data bhi.
- **Vikalp:**
  - **(a) Abhi jaisa:** har service ki apni chaabi live env me; kholna break-glass facade se.
  - **(b) Sirf band karne wali (public) chaabi server pe:** kholne wali (private) chaabi password manager me aur ek doosri offline copy; kholna sirf laptop ke break-glass command se.
  - **(c) Sirf FY ki file ke liye (b), baaki (a).**
- **Salah:** **(b)**. Ye data roz kabhi nahi khulta, to server ko kholne ki zaroorat hi nahi; leak hone pe bhi band data band rehta hai.
- **Trade-off:** (b) me kanooni maang pe kholna sirf owner ke laptop se, aur chaabi kho jaaye to band data aur purane FY ki books hamesha ke liye band (do offline copies aur saal ka abhyaas zaroori, R-078). (a) me server ke ek leak pe sab khula. (c) beech ka.
- **Kanooni detail:** Lawyer (AI) ne nahi jaancha: kanooni maang pe data kitni der me dena hota hai, aur laptop wala raasta us samay me chalega ya nahi.
- **R1:** haan (rok ki copy R1 me banti hai).

### S2-2. Audit aur logs ke database ka dhaancha (TTL, validators) kaun badle?

- **Sawal:** audit aur logs ke clusters me indexes, TTL aur validators ka badlav har boot pe live server ke release step se ho (baaki services jaisa), ya sirf owner ke laptop ke release command se?
- **Kyun zaroori:** boot ka release step ek release user se chalta hai jiske paas TTL badalne ka haq hai, aur wo user live server ke env me rehta hai. Hamlavar us user se audit ya logs ka TTL bahut chhota karke sab mita sakta hai, "sirf insert" wale user ke bawajood. Audit hi staff ke kaam ka saboot hai.
- **Vikalp:**
  - **(a) Abhi jaisa:** boot pe, release user live env me; bachav sirf audit chain ka hash bahar likhna (pakadna, rokna nahi).
  - **(b) Audit aur logs ke liye sirf laptop:** boot pe in dono me sirf jaanch (fingerprint na mile to alert, badlav nahi); badlav laptop ke command se, alag credentials se. Baaki services boot pe hi.
- **Salah:** **(b)**, saath me hash bahar likhna bhi. Audit aur logs ka dhaancha kam badalta hai, to haath ka kadam kabhi-kabhi hi aata hai.
- **Trade-off:** (b) me audit ya logs ke schema badlav wale release me owner ka ek haath ka kadam, aur bhoolne pe alert tak purana dhaancha. (a) me koi haath ka kaam nahi, par mitana sambhav (sirf baad me pata chalta).
- **R1:** haan.

### S2-3. Raat ke alerts ki push subscription kab tak rahe?

- **Sawal:** Master app me owner ke alerts ki push subscription session ke saath khatam ho (baaki khabron jaisa), ya device ke saath rahe jab tak owner khud na hataye?
- **Kyun zaroori:** gambhirta 1 ke alerts raat me push se aate hain. Abhi ka niyam subscription ko session se baandhta hai, aur staff ka session 12 ghante ka hai, to agle din se raat ke alerts chupke se band ho sakte hain.
- **Vikalp:**
  - **(a) Session ke saath** (abhi jaisa): session khatam, push band.
  - **(b) Device ke saath, sirf owner ke alerts:** session khatam hone pe bhi rehti hai; sirf "is device pe alerts band", device hatane ya account band hone pe hat-ti hai; payload me koi detail nahi.
- **Salah:** **(b)**, saath me subscription khatam hone pe gambhir email aur roz ka test push.
- **Trade-off:** (b) me band session wale device pe bhi "alert hai" ki khabar dikhti hai (bina detail); device chori pe "My devices" se hatana padta hai. (a) me raat ke alert ka bharosa nahi.
- **R1:** haan.

### S2-4. Request logs kaun aur kaise padhe?

- **Sawal:** logs service ke request logs (IP, account id, route, samay; 180 din, 2027 se 1 saal) kaun padh sakta hai?
- **Kyun zaroori:** logs me har user ka IP aur har kaam ka samay hai: ye personal data hai, aur incident ya kanooni maang pe yahi saboot hai. Padhne ka haq tay nahi, aur bina niyam ke ye staff ke liye sabse bada "sab ki jaankari" ka raasta ban sakta hai.
- **Vikalp:**
  - **(a) Sirf laptop ka command:** owner, alag credentials se.
  - **(b) Master app me sirf owner:** `logs.read` permission, dobara code, wajah, ek samay-khidki ya request id se khojna, har padhna audit me; bulk export nahi.
  - **(c) (b) + Support Lead:** sirf apne maamle ke request id se.
- **Salah:** **(b)**. Incident me tez, aur har padhne ka record.
- **Trade-off:** (a) me har jaanch laptop pe aur dheemi; (b) me Master app ki ek screen ka kaam; (c) me zyada log, zyada jokhim.
- **Kanooni detail:** Lawyer (AI) ne nahi jaancha: logs me IP ka personal data hona, aur CERT-In ya kisi kanooni maang pe logs dene ka samay.
- **R1:** haan.

### S2-5. Security bug ka private record kahan rahe?

- **R1:** haan.

### S2-8. Kam jaankari wale requests ki log line ya ginti?

- **Sawal:** Render ke host pe aaye rejected requests (bina secret ke `/api`, jinka jawab 403) aur `/wake` ki pings ki har request ki log line bane, ya baadh ke dauraan per IP har minute ki ek ginti?
- **Kyun zaroori:** Render ka host sabke liye khula hai. Koi bhi sasti requests ki baadh bhej ke logs ka 0.5 GB aur mahine ki 5 GB bandwidth khaa sakta hai; har khule tab ki ping bhi har 10 minute ek line banati hai.
- **Vikalp:**
  - **(a) Har request ki line** (abhi jaisa).
  - **(b) Aam din har line; ek IP se seema (misaal 100 requests/minute) ke upar sirf ginti** (pehla aur aakhri samay, ginti, route).
  - **(c) In dono qism ki hamesha sirf ginti.**
- **Salah:** **(b)**.
- **Trade-off:** (a) me poora record par baadh pe logs ki jagah khatam; (b) me baadh ke dauraan har request alag nahi dikhti; (c) me sabse kam jagah par sabse kam detail.
- **Kanooni detail:** Lawyer (AI) ne nahi jaancha: CERT-In ke logs ke niyam me ginti wala record chalta hai ya har request ki line chahiye.
- **R1:** haan.

### S2-9. Payment screen pe gateway ki script kaise alag rahe?

- **Sawal:** Customer app SPA hai (ek HTML document). Payment gateway ki checkout script ko baaki app se kaise alag rakhein?
- **Kyun zaroori:** browser ki CSP poore document ki hoti hai, route ki nahi. Ek baar load hui gateway ki script baaki screens (cart, address, orders) ke saath rehti hai, aur uske hosts poore app ki CSP me jaate hain. Abhi ka niyam "sirf payment page ki CSP me" SPA me poora nahi ho sakta.
- **Vikalp:**
  - **(a) Payment screen alag HTML document:** wahan aana-jaana poore page ka load; CSP aur gateway ki script sirf wahan.
  - **(b) Gateway ka apna hosted payment page (redirect):** hamare kisi page pe gateway ki script nahi.
  - **(c) Poore Customer app ki CSP me gateway ke hosts,** jokhim maan ke.
- **Salah:** **(a)**. Checkout ka roop (D-345) waisa hi, aur bahar ki script sirf ek chhote document tak.
- **Trade-off:** (a) me Payment pe aate-jaate ek poora page load aur app ki state wahan nahi (sirf order ka id); (b) me sabse kam jokhim, par customer app se bahar jaata hai aur test mode me raasta jaanchna baaki (F2-11); (c) me sabse aasaan, par bahar ki script ka asar poore app pe (R-016).
- **R1:** haan.
